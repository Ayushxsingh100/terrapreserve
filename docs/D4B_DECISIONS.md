## Decisions

| ID | Decision | Status | Reason | Rests on |
|---|---|---|---|---|
| D4-01 | Test split withheld. The repository is public (C-81). Only the dev split and the generator are committed. Test-split scenarios (including their reserves) are written to a private directory outside the repository (`$TERRAPRESERVE_PRIVATE`, default `~/.terrapreserve-private`), and the repository carries only `scenarios/test_manifest.json` with, for each test scenario, its id and the sha256 of its `scenario.json` and of each step directory. They are released with the dataset at paper submission (D0 Decision 9). | Decided | D0 Decision 9; DAIL C-82 for TerraPreserve settled; authors record it in DAIL's register. | D0 Decision 9; DAIL C-82; `scenarios/test_manifest.json` |
| D4-02 | Derived natives. The real-world tier will include a derived set of redacted natives (literal database password replaced by `var.db_password`, licence notice kept, `derived: true`). That is D4b; do nothing for it here except keep the scenario schema able to carry `derived` and `grafted` flags. | Decided | D4b scope; schema extensibility now prevents a breaking change later. | D4b scope; scenario schema `derived`, `grafted` fields |
| D4b-01 | Counts and fallback. Real-world tier: 16 cells x 13 = 208 scenarios (160 targets + 48 reserves), one base module per scenario, never reused. Natives (including derived natives) are used wherever their preconditions fit a cell's operator; hosts fill the rest. If a cell cannot be filled, report the actual count and do not pad (D0 fallback rule says the gap is filled with controlled scenarios; do not do that now: report the gap, D6 decides). | Proposed | D0 Decision 2 (320 benchmark scenarios); D0 Decision 3 (fallback rule: actual counts reported, never padded). | D0 Decisions 2, 3; D4b Plan |
| D4b-02 | Derived natives. Candidates: native-candidate (F3, permissive) modules excluded as E09 whose findings are only a literal password attribute on an `aws_db_instance` (the 96). Transform, per module: replace the literal with `var.db_password`; add `variable "db_password" { type = string sensitive = true }` with no default; if the module already declares `db_password` or the literal also appears anywhere else, do not derive it (code DX01, listed). Then rescan (gitleaks + attribute inventory, both must find nothing), then re-run E03-E08, E10 (lineage against the pool and among the derived ones), E11 (licence), E12 (validate under the pins) on the derived text. Output kept apart from D3's files: `pool/terrads/derived/<module_id>/`, `pool/derived.json`, `pool/derived_exclusions.csv`. `DERIVED.md` logs each change by file, line, resource address, attribute name and the sha256 of the file before and after, never a value. No secret value is stored anywhere. D3 committed files stay unchanged. | Proposed | D4-02; D0 Decision 3 (native first, graft the rest); safe redaction without secret leakage. | D4-02; `pool/exclusions.csv`; `sources/acquire.py` |
| D4b-03 | Graft. A host's files are copied as D3-09 validated them (top-level terraform and provider blocks removed with `hcl_lex.remove_top_level_blocks`, plus the pin file `terrapreserve_versions.tf`), and the scenario records this transform and the sha256 of each original file. The canonical core is added as separate files (`terrapreserve_graft.tf`, `terrapreserve_graft_variables.tf`) emitted by the D4a emitter from the D4a model: standalone VPC, subnets, IGW, route table, SGs, EC2, RDS, every name prefixed `tp_` (resources and variables, e.g. `tp_db_password`), checked against all of the host's addresses, variable, local, output and module names (a clash is a hard error, never a rename-and-continue). The graft does not attach to the host's own network in v1 (see Open row 1). `grafted: true`. | Proposed | D0 Decision 3 (grafting step provides testable functional invariant inside real-world context). | D0 Decision 3; `generator/emitter.py`; `generator/model.py` |
| D4b-04 | Operators on hosts. All 50 D4a operators are reused unchanged and act on the graft's model; host files are never edited, so a host's mutation record is as truthful as in D4a. The real-world context is therefore the surrounding module, not mutated code (state this limit in `DATASHEET.md`). | Proposed | Truthfulness of mutation records; preservation of validated host structure. | `generator/operators/__init__.py`; `DATASHEET.md` |
| D4b-05 | Operators on natives. Natives have real, non-canonical HCL, so operators cannot work on the D4a model. Define a small span-edit layer: an operator names its target resource address and attribute, checks preconditions with `hcl_lex` (the attribute exists, its value is a literal of the expected kind, the block is not count/for_each/dynamic), and replaces exactly the value's character span. Minimum operator coverage on natives: F1, F2, F4, F6 (new resource in an added file), F8 (chain of span edits); F3, F5 and F7 need structural edits and go to hosts unless you can do them safely. Each operator keeps the D4a contract (family, variant, intent.breaks / intent.preserves, exact mutation rows) and is documented in `docs/D4_OPERATORS.md` before the code. Applicability is decided by preconditions, not by hand; a native that fits no operator for a cell is simply not used for that cell. | Proposed | Safe mutations on non-canonical text without AST corruption. | `sources/hcl_lex.py`; `docs/D4_OPERATORS.md` |
| D4b-06 | Verifier for real text. `generator/diff_verify.py` reads canonical emitted text. Add a second verifier for non-canonical text built on `hcl_lex` that recomputes, from the text of step k-1 and step k, the changed `(address, attribute)` pairs and fails if the record omits a change or invents one. Whole-file comparison also checks that nothing else changed (any byte outside the recorded spans is identical). Same standard as D4-08. | Proposed | Non-fabrication and truthfulness of mutation records for real-world modules. | `generator/diff_verify.py`; `sources/hcl_lex.py` |
| D4b-07 | S0 eligibility screen (a screen, not a label). Before using a native, read it lexically: reject (code `RW-S0`, listed) a native whose in-scope resources show a literal ingress from `0.0.0.0/0` or `::/0` on 22 or 5432, or `publicly_accessible = true`, unless that is the scenario's repair target. Anything not decidable by the lexical reader (variables, locals, dynamic) is recorded as unknown, not guessed. The oracle (D5) decides the truth; D6 swaps in reserves when the oracle disagrees with the intent. | Proposed | D0 Decision 6 (S0 satisfies all invariants except repair target); lexical screening avoids wasted oracle cycles. | D0 Decision 6; `sources/hcl_lex.py` |
| D4b-08 | Split. Lineage is the unit (D3-07). Assign each module (native, derived native, host) to dev or test by lineage, once, with `random.Random(20261031)` over lineage ids in sorted order, 70/30; write `scenarios/split_real_world.json` (lineage id to side). Fill each cell so that its targets are 7 dev + 3 test and its reserves 2 dev + 1 test, as in the controlled tier, drawing modules only from the correct side. A module never changes side. Verify that no lineage appears in both sides across both tiers (controlled template ids are different namespaces; check that anyway). | Proposed | D0 Decision 7 (lineage split 70/30, no leakage across splits). | D0 Decision 7; D0 Gate 6; `pool/lineage.py` |
| D4b-09 | Cell assignment. Deterministic: iterate cells in a fixed order, for each slot take the first eligible module in a seeded order, natives before hosts (user decision). Report per cell how many natives, derived natives and hosts were used. | Proposed | Reproducible, deterministic assignment prioritizing native real-world paths. | D0 Decision 3; `scenarios/split_real_world.json` |
| D4b-10 | Scenario record. Same schema as D4a plus, for the real-world tier: `source.tier = "real_world"`, `source.origin = "terrads"`, `source.repo_lineage_id`, `source.commit_or_version` (the pool commit sha), `source.license` (SPDX), `source.grafted`, `derived`, `module_id`, `pool_id`, `host_transform` (list of what was removed, with original file hashes), `scope_addresses` (see Open row 2), `s0_screen` (from D4b-07). `gt_class`, `labels`, `oracle` are null. | Proposed | D0 Decision 6 (canonical scenario schema); D4b provenance. | D0 Decision 6; `generator/writer.py` |
| D4b-11 | Licences and notices. Every real-world scenario keeps its module's licence file (`LICENSE.upstream`) and `SOURCE.json` in `step_0/`-adjacent provenance (e.g. `scenarios/dev/<id>/PROVENANCE/`). Because host and derived files are modified (provider/terraform blocks removed, password replaced), `scenarios/NOTICE` states the modification in a form that satisfies Apache-2.0 section 4(b) and keeps MIT/BSD/CC0/Unlicense notices. Our own graft files are CC-BY-4.0. | Proposed | D0 Decision 9 (preservation of upstream licences and notices). | D0 Decision 9; Apache-2.0 section 4(b); `scenarios/NOTICE` |
| D4b-12 | Reproducibility. Same rules as D4-12: master seed, a `random.Random` per scenario derived by hashing (master seed, scenario index), two full runs byte-identical. The generator version becomes `d4b-1` for real-world scenarios; the controlled tier files must stay byte-identical to the D4a commit (prove it with a test that regenerates the controlled dev tree and compares with `scenarios/dev/` as committed at 8fc4e36). | Proposed | Criterion A10; R4 reproducibility. | `generator/seed.py`; D4-12 |
| Open 1 | Graft attachment. D0 says the graft "keeps real-world context (real naming, real SG and network patterns)". D4b-03 grafts a standalone core next to the host, which keeps the host's files and names but does not connect the core to the host's network. Attaching to the host's VPC and subnets is more realistic but depends on variables, count and for_each the lexical reader cannot evaluate. Authors decide whether standalone is acceptable for v1.0 or whether attach mode is a v1.1 item. | Open | Structural limits of static lexical analysis on arbitrary Terraform. | D0 Decision 3; D4b-03 |
| Open 2 | Invariant scope on a real module. D0 Decision 4 states the invariants without saying which resources they range over when a module has many unrelated security groups. D4b-03/05 record `scope_addresses` (graft: the graft's own addresses; native: the SG, SG rule, EC2 and RDS addresses of the module) so that S0 can be "clean except the target" for the part that matters. The D5 oracle must evaluate within that scope. This must be confirmed by the authors and written into the registry v1.1 amendment (C-150, C-155) before D5. | Open | Ground-truth definition ambiguity in multi-resource real-world modules. | D0 Decision 4; D4b-10; D5 scope |
