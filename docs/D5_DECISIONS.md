# D5 decisions: The oracle (D5a groundwork, D5a-2, D5a-3, D5b)

Decisions for work packages D5a (variable values, input-path feasibility, oracle skeleton) D5a-2 (every step plannable offline: typed values, data-source variables, two value sets) D5a-3 (value rule vv-3, then exclusion of what still cannot plan) and D5b (the oracle and the labelling run). `Proposed` rows are the work package design, followed as written; where D5a-2 had to fill a gap in the design, the row says so and why. `Decided` rows were decided by the authors (9 Nov 2026; D5-11, the D5-09 amendment, Open D5-D and D5-22 on 10 Nov 2026). Rule vv-1 (D5-01) is superseded by vv-2 (D5-07), and vv-2 by vv-3 (D5-10); the generator uses only vv-3. The superseded rows are kept as the record of D5a and D5a-2. Cells contain no pipe characters, so the table stays mechanically parseable.

The specification is the DAIL Invariant Registry, `docs/specs/INVARIANT_REGISTRY_v1.md` at tag `registry-v1.0`, read as a specification only (CLAUDE.md rule 7). Section 2.1: "The input is one Terraform root-module configuration directory together with the scenario's variable values." Section 2.2: an input variable resolves to its "provided value, else declared default". The work package cites section 2.2 for the first sentence; the sentence itself is in section 2.1.

| D5-01 | Variable values in the scenario record. Every `scenario.json` gets `variable_values`: one object for the whole scenario (all steps), mapping each variable declared without a default to a value chosen by the fixed, versioned rule `vv-1` (`variable_values_rule: "vv-1"`). Variables with a default are not listed (the default applies). By declared `type` when present, else as string: `string` gives `"tp-placeholder"`, `number` gives `1`, `bool` gives `false`, `list`, `set` and `tuple` give `[]`, `map` and `object` give `{}`. A variable that is `sensitive = true` or whose name contains `password`, `secret` or `token` gives `"tp-placeholder"`. A value that cannot satisfy the type goes under `variable_values_unresolved` with the reason, and no value is invented. That covers an `object` with a required attribute, a non-empty `tuple`, a type the rule does not cover (`any`), a secret-named variable of a non-string type, and a value a `validation` block rejects. Validation blocks are checked by Terraform itself: the single variable block is planned in an empty directory with the candidate value, with no provider and no network. Steps are not changed; only `scenario.json`. Generator versions are `d4a-5` (controlled) and `d4b-6` (real-world). A variable's candidate index applies to all its leaves: a leaf at index i takes its kind's candidate min(i, last). Its number of candidates is the longest list among its leaf kinds (at most 4). A step that times out (600 s, an environment effect, not a verdict on a value) is planned again up to twice more before its result counts. At the first step that fails with a Terraform error (first line `Error:`; a timeout or a run without an error line moves nothing), the variables of the first error block are found: those it names (`var.<name>`, `variable "<name>"`), those reached through a `local.<name>` it names, and those one of whose current string values it contains. Each such variable with a declared default not yet overridden is overridden (rule 1; the override then holds in both sets, since the default is the same in both); each valued one not at its last candidate moves to its next candidate (rule 2). The alternate set skips a candidate whose whole value equals the primary's, unless the vv-2 record states a same-in-both-sets reason. Then all steps are planned again from step 0. When no named variable can change, the search for that set ends. The search is deterministic (same files, same order, same candidates taken) and ends after at most 3 moves per variable per set. Its result is stored per split (`generator/vv3/dev.json`; the test split's in `$TERRAPRESERVE_PRIVATE/vv3_test.json`) and the generator builds each record from it. | D5-11 | gt_class rule.
