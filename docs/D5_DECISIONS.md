# D5 decisions: The oracle (D5a groundwork, D5a-2)

Decisions for work packages D5a (variable values, input-path feasibility, oracle skeleton) and D5a-2 (every step plannable offline: typed values, data-source variables, two value sets). `Proposed` rows are the work package design, followed as written; where D5a-2 had to fill a gap in the design, the row says so and why. `Decided` rows were decided by the authors (9 Nov 2026). Rule vv-1 (D5-01) is superseded by vv-2 (D5-07) and is no longer used by the generator; its row is kept as the record of D5a. Cells contain no pipe characters, so the table stays mechanically parseable.

The specification is the DAIL Invariant Registry, `docs/specs/INVARIANT_REGISTRY_v1.md` at tag `registry-v1.0`, read as a specification only (CLAUDE.md rule 7). Section 2.1: "The input is one Terraform root-module configuration directory together with the scenario's variable values." Section 2.2: an input variable resolves to its "provided value, else declared default". The work package cites section 2.2 for the first sentence; the sentence itself is in section 2.1.

## Decisions

| ID | Decision | Status | Reason | Rests on |
|---|---|---|---|---|
| D5-01 | Variable values in the scenario record. Every `scenario.json` gets `variable_values`: one object for the whole scenario (all steps), mapping each variable declared without a default to a value chosen by the fixed, versioned rule `vv-1` (`variable_values_rule: "vv-1"`). Variables with a default are not listed (the default applies). By declared `type` when present, else as string: `string` gives `"tp-placeholder"`, `number` gives `1`, `bool` gives `false`, `list`, `set` and `tuple` give `[]`, `map` and `object` give `{}`. A variable that is `sensitive = true` or whose name contains `password`, `secret` or `token` gives `"tp-placeholder"`. A value that cannot satisfy the type goes under `variable_values_unresolved` with the reason, and no value is invented. That covers an `object` with a required attribute, a non-empty `tuple`, a type the rule does not cover (`any`), a secret-named variable of a non-string type, and a value a `validation` block rejects. Validation blocks are checked by Terraform itself: the single variable block is planned in an empty directory with the candidate value, with no provider and no network. Steps are not changed; only `scenario.json`. Generator versions are `d4a-5` (controlled) and `d4b-6` (real-world). The same values will be used by the oracle and, later, by DAIL in P8. | Superseded | Superseded by D5-07 in D5a-2; vv-1 is no longer used. Registry v1.0 sections 2.1 and 2.2 evaluate with the scenario's variable values, and no scenario carried any (`docs/D5_CARRYOVER.md` section 6.2). A fixed rule keeps the oracle and DAIL on the same configuration. | D5a work package; `generator/varvalues.py`; `tests/test_d5a_variable_values.py` |
| D5-02 | Oracle layout. `oracle/` is a package with `VERSION.py` (`ORACLE_VERSION = "oracle-0.1"`), `inputs.py`, `record.py` and `README.md`. `inputs.py` builds the oracle's private working copy of a step: the step's `.tf` files, an oracle-only provider block, and `terraform.tfvars.json` from `variable_values`. It never writes into `scenarios/` (or into the private test split). `record.py` writes the D0 Decision 6 `labels` and `oracle` structures. In D5a it writes only `null` truth values, in a dry run, and never real labels. | Proposed | D0 Decision 6 label schema; D0 Decision 10 gate 9 (versions recorded). | `oracle/`; `tests/test_d5a_oracle_skeleton.py` |
| D5-03 | Independence. No file under `oracle/` imports from `generator/`, `pool/`, `sources/`, `tests/` or `tools/`, and none imports DAIL. The test allows only the standard library and `oracle` itself, and forbids `sys.path` edits. No file outside `oracle/` and `tools/` may write a non-null `labels`, `gt_class` or `oracle` field (setting them to `null`, as the generator does, is not a write of ground truth). The generator's `modread.py` and the tests' self-check evaluators are never imported by the oracle. Each rule is shown to fail on a planted violation in a scratch copy (`tools/run_d5a_independence_mutations.py`). | Proposed | DAIL ADR-010; CLAUDE.md rules 5 and 7; D0 gate 1. | `tests/test_independence.py`; `tools/run_d5a_independence_mutations.py` |
| D5-04 | Offline plan, no credentials. The oracle-only provider block uses `region = "us-east-1"`, static placeholder strings for the access key and secret (built at run time, never real, not credential-shaped), `skip_credentials_validation`, `skip_requesting_account_id`, `skip_metadata_api_check` and `skip_region_validation` set to `true`, and (an addition to the work package text, found necessary in Step 4) `max_retries = 1`, so that an attempted AWS call fails on its first refusal instead of being retried with back-off until the 600 s step timeout; it makes no step plan that would not plan anyway. `terraform init` uses the offline provider mirror used in `validation/` (`~/.terrapreserve-cache/tf-mirror`), through an oracle CLI configuration with that filesystem mirror only, so nothing is downloaded from the registry. Commands run with no AWS environment variables, with `AWS_SHARED_CREDENTIALS_FILE` and `AWS_CONFIG_FILE` set to empty temporary files, and with `AWS_EC2_METADATA_DISABLED=true`. HTTP and HTTPS proxies point at a closed local port, so any attempt to reach an AWS endpoint fails on this machine and is recorded as a failure. | Proposed | Never use AWS credentials (CLAUDE.md); no network call to AWS (D5a Do Not Do). The proxy guard, `max_retries = 1` and the mirror-only CLI configuration implement "no network call", and are additions to the work package text. | `oracle/inputs.py`; `tools/run_d5a_feasibility.py` |
| D5-05 | Plan JSON is the oracle's only input path. The oracle reads `terraform show -json <planfile>` for every step; there is no HCL fallback in the oracle. Every step must therefore be plannable offline (D5-04 rules); D5a-2 makes the steps so (D5-07, D5-08) and measures it for both value sets. | Decided | Decided by the authors on 9 Nov 2026 (Open D5-A). Registry section 2.1: "The oracle uses a different input path from DAIL (ADR-010)", and DAIL parses HCL. | D5a-2 work package Section 2; registry v1.0 section 2.1 |
| D5-06 | Invariance test. Every value the project invents (variable values and data-source values) exists in two independent sets, a primary (`variable_values`) and an alternate (`variable_values_alt`). In D5b every scenario is labelled under both sets; a scenario whose oracle labels differ between the sets depends on an invented value and is excluded from v1.0 (D6 fills from reserves; the count is reported, never padded). D5a-2 builds the two sets and measures that both plan; it labels nothing. | Decided | Decided by the authors on 9 Nov 2026 (Open D5-B). A label that changes with an invented value is not a property of the scenario. | D5a-2 work package Section 2 |
| D5-07 | Value rule vv-2 (replaces vv-1). `scenario.json` carries `variable_values` (primary), `variable_values_alt` (alternate), `variable_values_rule: "vv-2"`, `variable_values_kinds` (per variable: `kind`, `evidence`, and when present `validation` with the candidate taken in each set and `same_in_both_sets` with the recorded reason) and `variable_values_unresolved` (per variable: `status` `unresolved` or `conflict`, and `reason`). Both sets cover every variable declared without a default, the D5-08 `tp_ds_*` variables included. Kinds and values follow the work package table (`generator/varvalues.py` `KIND_VALUES`, `ATTR_KINDS`): the declared type first (recursively; an object gets every required attribute); for a string leaf, `secret` when the variable is sensitive or its name contains password, secret or token, else the attributes the value flows into (directly or through a local); `number` 1 and 2, `bool` false and true; empty-able collections `[]` or `{}` and a one-element collection. Validation blocks are checked by Terraform in an empty directory; a rejected value moves to the next candidate (the kind's value, then the string literals the validation names in `contains([...], var.x)` or `var.x == "..."`, in written order), and the alternate takes the first accepted candidate that differs from the primary. The `region` kind is `us-east-1` in both sets (recorded). The `secret` kind is `tp-secret-primary` and `tp-secret-alt`, not the work package's `TpPrimaryPlaceholder1` and `TpAltPlaceholder2`: gitleaks (default rules, `generic-api-key`) reports those two strings as leaked secrets next to a password-named key (594 findings in `scenarios/`), and the authors chose on 9 Nov 2026 to change the values rather than the gitleaks configuration. Controlled tier: only `db_password` (kind `secret`). Gaps the design left open, filled here and recorded so the authors can change them: (1) a collection the configuration indexes (`x[i]`, `tolist(x)[i]`, `element(x, i)`) cannot be empty, so it gets 3 elements in both sets (more if a constant index needs it); 3 is a fixed constant, chosen so that the indexes the configurations use are in range; (2) `string` is the fallback, so a conflict is two different table kinds, and a use inside a string template with other text counts as `string`; (3) uses through `for_each`/`each.value` and dynamic-block iterators count as uses of the iterated variable; (4) an untyped or `any` part takes its structure from its uses; a map indexed by a computed key is `unresolved`; (5) argument names beyond the table's examples count as the same kinds (`destination_cidr_block`, `cidr_ipv4` as `ipv4_cidr`; `ipv6_cidr_block`, `cidr_ipv6` as `ipv6_cidr`; `security_groups`, `security_group_ids`, `source_security_group_id`, `referenced_security_group_id` as `sg_id`); (6) data-source attributes take their kind from the data source's schema (`DS_KINDS`) before their use. Generator versions `d4a-6` (controlled) and `d4b-7` (real-world). | Proposed | Under vv-1 the placeholder `tp-placeholder` reached CIDR, id and AZ arguments and 104 dev steps failed on a variable error (`docs/D5A_FEASIBILITY.md`, D5a part). Typed values make the configurations plannable; a second, independent set is what D5-06 needs. | D5a-2 work package Section 3; `generator/varvalues.py`; `tests/test_d5a2_value_sets.py` |
| D5-08 | Data-source variables, a recorded host transform (real-world tier). For every `data "<type>" "<name>"` block in a module (host or native, every step), the generator removes the block, replaces every reference `data.<type>.<name>` (with any path or index after it, in expressions, strings and heredocs) by `var.tp_ds_<type>_<name>` with the same path, and declares that variable with no default in `terrapreserve_data_variables.tf`, typed as an `object` with exactly the attributes the module uses (nested as used; a `list(...)` of it for a block with `count`, a `map(...)` for `for_each`; attributes that are lists in the provider schema are typed `list(string)`). The variable's `description` names the replaced block. Comments are not configuration and are left as written. Each removal is recorded in `host_transform` (`kind: "data_source_to_variable"`, `file`, `data_type`, `data_name`, the sha256 of the original block text from the `data` keyword to its closing brace, `variable`). vv-2 gives the variables both values. `terraform_remote_state` is handled the same way (its `outputs` become an object attribute). Hosts are not re-selected: the whole-module S0 screen runs on the transformed module, and a host that fails it stops the package. | Proposed | D5-05 needs every step to plan offline, and a data source needs the AWS API. The transform changes host text, so DAIL (later, P8) and the oracle read the same configuration. | D5a-2 work package Section 3; `generator/realworld/data_vars.py`; `tests/test_d5a2_value_sets.py` |
| Open D5-A | Input path for steps that cannot be planned offline. Decided by the authors after the Step 4 numbers (`docs/D5A_FEASIBILITY.md`): see D5-05. | Decided | The project plan has the oracle read the plan JSON (`terraform show -json`), a different input path from DAIL (registry section 2.1, ADR-010). Whether an offline plan is possible for every step is measured in D5a, not assumed. | Registry v1.0 section 2.1; D5a Step 4 |

Decided by the authors after the Step 2 relevance report (`docs/D5A_FEASIBILITY.md`): see D5-06. | Decided | Where a vv-1 placeholder reaches an attribute the registry reads, the placeholder choice could change a label. | D5-01; D5a Step 2 |
